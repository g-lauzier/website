When a work is generated by a system, where should we look for the artist’s contribution? In the code, the choice of inputs, the selection of outputs, or the context in which the result is presented? Often, it is distributed across several of those decisions.

The word “authenticity” can obscure that discussion because it bundles together different questions. A work can have a documented origin without being artistically compelling. It can be meaningful to an audience without involving original code. And its creative value does not, by itself, establish its legal status.

I find it more useful to ask what the artist intended, which decisions they made, and how honestly the work describes its process. That approach leaves room to evaluate a specific practice without ranking every work by the amount of code its maker wrote.

## Blur between "No Code Art", and "Creative Coding"

A visual tool can expose parameters, nodes and rules without requiring text-based programming. An artist may use those controls to define a distinctive process, or may use an existing preset with little modification. The tool category alone does not tell us which happened.

Creative coding makes programming part of the artistic practice. That can offer precise control over behavior, but it also creates practical work: debugging, coordinating timing, managing dependencies and translating a visual idea into executable rules. Writing custom code is an opportunity to shape the process, rather than a guarantee of originality.

Collaboration complicates the picture in a productive way. One person might design the system, another supply a dataset, and another develop the performance or installation. Clear credits make those contributions legible instead of attributing everything to the person whose name appears beside the final image.

For a viewer, useful documentation includes sketches, parameter studies and an explanation of what changed between iterations. A gallery of selected outputs can show the artist’s judgment. A reproducible example can show what the system contributes.

Reproducibility is compatible with generative work. For example, p5.js provides [a seed mechanism](https://p5js.org/reference/p5/randomSeed/) that can repeat a pseudorandom sequence. A work does not need to be impossible to reproduce in order to be distinctive.

## "No Code" and "Creative Coding" hybrids

Many workflows combine existing software with custom interventions. An artist might build a visual composition in a node editor, add a script that controls how it responds to sound, and select a short sequence for exhibition. Another might write the generator but use familiar image-editing tools to prepare the print.

In each case, the useful questions are concrete: which parts are inherited, which are changed, and which decisions account for the character of the finished work? Describe the tool, model or library version where it matters, credit source material, and explain the role of selection or manual editing.

An aesthetic judgment about originality should also be separated from a claim to exclusive rights. As one jurisdiction-specific example, the [U.S. Copyright Office’s 2025 AI report](https://copyright.gov/newsnet/2025/1060.html) distinguishes human expression from material generated by AI and explains that using AI does not automatically disqualify the human-authored elements of a work. That legal question is narrower than whether an audience finds the work authentic or worthwhile.

For me, the strongest account of authenticity is an honest account of decisions. The work should withstand curiosity about how it was made. That curiosity can deepen appreciation of the artist’s contribution, including when the process combines code, borrowed tools and collaboration.
